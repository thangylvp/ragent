# RAGENT end-to-end demo design

> Version 0.2 implements this composition with the existing car checkpoint and
> a simulated car-shaped digital twin. The interfaces are the intended robot
> boundaries; the visible fields and tool catalog will change when the robot
> contract is frozen.

## Purpose

The demo is a human-operated integration test for the VAD, SLM, agent harness
and execution layer. Component evaluations remain authoritative for accuracy;
the demo exposes boundary mistakes, turn-taking failures, state drift and
latency that isolated tests cannot show.

It must remain thin. Business logic belongs in `src/vad`, `src/harness` or
`src/execute`; `demo/backend/model.py` owns only the vLLM transport adapter.
The demo composes those boundaries and renders their events.

## Differences from the car demo

| Car `stc` demo | Robot demo |
| --- | --- |
| Click once to start and once to stop recording | Continuous PCM stream with server-side VAD; push-to-talk remains a diagnostic fallback |
| Car HMI controls dominate the page | Conversation, robot mission/motion/safety state and action timeline dominate |
| Car simulator is called directly by demo pipeline | Harness calls the execution-layer interface; the demo never bypasses it |
| Browser produces a complete WAV before upload | Browser sends fixed PCM frames; VAD emits a finalized utterance |
| Cabin-specific reducers | Schema-driven robot state snapshot plus generic events until the catalog is frozen |

## End-to-end flow

```text
getUserMedia
  -> AudioWorklet (mono PCM frames)
  -> WebSocket /api/audio/stream
  -> vad.VadEngine + segmenter
  -> completed utterance
  -> standalone SLM through vLLM (or disabled for VAD isolation)
  -> harness conversation loop
       -> non_tool -> cloud adapter -> reply -> laptop OmniVoice TTS
       -> one tool call -> execute gateway
            -> success/missing/reject/busy -> local prerecorded WAV
  -> structured stage events over the WebSocket
  -> conversation, robot-state and latency panels
```

Audio classification and endpointing happen on the server. The browser may
show a live RMS meter but must not decide the canonical start/end boundaries.
This ensures the page tests the first-class VAD component that will also
receive robot microphone audio.

## Turn state machine

```text
LISTENING
   │ VAD speech-ended/max-duration
   ▼
INPUT_GATED ── capture WAV ──► SLM_STREAMING
                                  │
                   ┌──────────────┴──────────────┐
                   ▼                             ▼
             CLOUD_REPLY                  VALIDATE + EXECUTE
                   └──────────────┬──────────────┘
                                  ▼
                         RESPONSE_AUDIO_READY
                                  │ browser `playing`
                                  ▼
                              PLAYING
                                  │ browser `ended`
                                  ▼
                  reset enhancer + VAD → LISTENING
```

The gate closes before any inference event is emitted. Binary packets already
queued in the WebSocket are drained while playback is pending and never enter
the next utterance. The gate opens only after the matching `turn_id` receives
`playback_finished`; a stale acknowledgement cannot reopen a newer turn.

## Response policy

| SLM/execution result | Harness action | Spoken response |
| --- | --- | --- |
| `non_tool(text=...)` | Send transcript and bounded history to Gemini | Dynamic Vietnamese TTS |
| Valid tool call, hardware ready | Execute simulator reducer | Cached tool-specific success clip |
| Required/actionable argument absent | Execute layer does not mutate hardware | Cached tool-specific follow-up question |
| Hardware busy | Do not execute | Cached busy clip |
| Invalid or state-rejected tool | Execute layer does not mutate hardware | Cached detailed tool/reason-specific rejection |
| More than one tool call | Reject the whole turn before execution | Cached one-command-at-a-time request |
| Abstain or malformed output | Do not execute | Cached repeat-request clip |
| Cloud unavailable | Do not retry TTS dynamically | Cached cloud-unavailable clip |
| Cloud reply succeeds but cloud TTS fails | Keep the text answer | Cached local TTS-unavailable clip |

The missing-field question is selected by deterministic code, not generated by
the SLM. The answer becomes a fresh SLM turn. The harness intentionally does
not retain a pending call, merge slots or send previous turns to this
single-turn checkpoint.

All deterministic sentences above are rendered before the demo and served
from a versioned, checksum-verified local manifest. Runtime TTS is used only
when a successful cloud turn returns text that could not have been known ahead
of time. Missing local audio is a packaging error; the browser does not mask it
with its own speech synthesizer.

The TTS boundary is one resident OmniVoice worker on the laptop. It loads
`splendor1811/omnivoice-vietnamese` once and creates one reusable clone prompt
from an authorized external reference clip plus its exact transcript.
Jetson calls this network service only for dynamic cloud-agent replies. The
Jetson client needs a base URL and stable voice ID, not laptop reference-audio
paths. Fixed clips are generated on the laptop and copied to Jetson with their
manifest; a text or checksum mismatch fails visibly instead of silently using
stale speech.

## Timing boundaries

`utterance_finalized` is the common zero point called **audio ready**. It is
after endpointing and before WAV retention. The server reports:

- audio ready → first meaningful streaming SLM delta;
- audio ready → last meaningful streaming SLM delta;
- capture, dispatch, SLM, cloud, execution and TTS/cache component time.

The browser measures audio ready → the first actual `playing` event because
only the playback device can observe decode, fetch and scheduler delay. It then
sends this client-observed value back with `audio_playback_started`. Endpoint
delay from physical speech end remains a separate VAD metric and is not hidden
inside these three demo cards.

## Transport contract

The microphone stream uses one WebSocket per session:

- client sends a JSON `start_stream` message with PCM format metadata;
- client then sends binary 16 kHz mono PCM16LE frames, normally 20 ms each;
- server emits `vad_frame`, `utterance_started`, `utterance_finalized`,
  `model_started`, `model_result`, `assistant_response`, input-gate and error
  events;
- `stop_stream` flushes or rejects the current segment deterministically;
- reconnect creates no implicit model turn and does not execute a partial call.

Typed text and uploaded WAV endpoints remain available to isolate microphone
or VAD failures during debugging.

Every finalized turn receives one `turn_id`. Stage events carry monotonic
timestamps so the UI can display:

- captured and retained audio duration;
- VAD onset confirmation and endpoint delay;
- SLM queue time, TTFT, decode time and output tokens/second when available;
- harness validation/follow-up time;
- execution or cloud latency;
- speech-end-to-result and total end-to-end latency.

## Page layout

The page has four primary areas:

1. **Conversation (left)** — tool turns render **User → SLM → AI**. Non-tool
   turns render **User → SLM → Cloud Agent → AI**. User owns only the retained
   playable model-input recording; SLM owns the route, raw output and parsed
   tool call/transcript; Cloud Agent owns the free-form cloud response and its
   model/latency; AI owns the final Vietnamese output audio. The AI result
   retains the three end-to-end latency milestones and component timing; no
   global last-turn result overwrites older turns. Input-audio preview
   temporarily pauses microphone transport so it cannot become a new request.
2. **Hardware (right)** — simulated state, latest actions and a busy switch;
   the current car-shaped twin is explicitly temporary.
3. **Technical drawer** — before/after enhancement audio, raw SLM output,
   component timings and event trace without dominating the demo.

The UI never fabricates a successful state change. Rejected, timed-out and
cancelled calls stay visible with the previous robot snapshot.

## Modes

- `mock`: CPU-only deterministic SLM, cloud and robot simulator; used by CI
  and frontend development.
- `local`: standalone speech-to-action checkpoint in the demo backend.
- `vllm`: OpenAI-compatible remote model server; harness and execute stay
  local unless explicitly configured otherwise.
- `robot`: real execution gateway; opt-in and visibly distinguished from the
  simulator. Actions still pass through execution validation and safety.

Real-robot mode must never be the default. The page shows an armed/disarmed
state and requires the execution layer to authorize actions; UI controls do
not constitute a safety mechanism.

## VAD test cases

The demo smoke suite replays continuous PCM streams with known boundaries:

- silence followed by one command and trailing silence;
- two commands separated by sufficient silence;
- short cough/tap that must be rejected;
- far-field command with fan or motor noise;
- a command immediately after robot TTS finishes;
- robot TTS while the half-duplex gate is closed;
- a long utterance reaching the configured maximum;
- disconnect during speech, which must not execute a partial call.

CI uses fake clocks and recorded fixtures. Hardware runs additionally report
VAD and end-to-end metrics from real-time streaming.
