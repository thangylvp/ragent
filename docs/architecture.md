# Architecture

## Scope

The model is a low-latency semantic parser built on a pretrained ASR model. It
accepts exactly the current audio turn and returns structured output. The
current SLM is single-turn: the harness never sends earlier audio, tool calls
or follow-up state into it. It never produces the final user-facing answer and
never executes a robot action.

```text
continuous microphone PCM
          │
          ▼
 acoustic echo cancellation (playback reference when available)
          │
          ▼
 first-class streaming speech enhancement
          │
          ▼
  first-class streaming VAD ◄────── harness playback/gate state
          │ completed utterance
          ▼
        harness turn controller
          │
          ▼
 Qwen3-ASR speech-to-action SLM
          │
   ┌──────┴──────────────┐
   │                     │
   ▼                     ▼
non_tool(text=...)   robot tool call (partial arguments allowed)
   │                     │
   ▼                     ▼
cloud agent              execution layer
   │                 schema + state + safety + I/O
   │                         │
   │             ┌───────────┼────────────┐
   │             ▼           ▼            ▼
   │          success   missing field   reject/busy
   │             └───────────┼────────────┘
   │                         ▼
   └────► dynamic TTS   cached Vietnamese response
```

Speech enhancement and VAD are first-class components at the same repository
level as the SLM. Enhancement transforms frames but does not define utterance
boundaries; VAD consumes the enhanced stream and owns endpointing. VAD
decides when an utterance becomes a model turn and exposes those events to the
harness. The SLM always receives a bounded utterance rather than an unbounded
microphone stream. The browser demo must use the same server-side VAD path
intended for robot audio; browser-side audio level visualization is not the
source of truth for endpointing.

## Model contract

For every completed audio turn, version 1 returns exactly one route:

- `non_tool` with the recognized Vietnamese transcript in `text`; or
- one robot function call with the tool name and every argument that the user
  supplied in the current turn or that is unambiguous from supplied context.

The model must:

- omit missing arguments rather than fabricate defaults;
- preserve corrections and self-repairs in speech (the last clear value wins);
- avoid resolving state-dependent references that require live robot state;
- use the tool catalog provided in the request unchanged;
- produce no natural-language answer outside the tool call.

Version 1 intentionally limits each turn to one route. Multi-action commands
will be evaluated before deciding whether to support parallel tool calls or
route them to the cloud agent.

## Harness contract

The agent harness owns the conversation loop. The first demo implementation
lives in `src/harness`; it receives the SLM
result and:

1. consumes completed utterance events from the VAD component;
2. controls the VAD listening gate around robot playback/cancellation;
3. forwards only the latest completed utterance to the single-turn SLM;
4. forwards `non_tool.text` and cloud conversation history to the cloud agent;
5. sends exactly one robot call to the execution layer per turn;
6. maps success, missing-field, rejected and busy results to deterministic
   prerecorded Vietnamese clips;
7. asks a cached follow-up when required information is absent, then treats
   the user's answer as a fresh, independent SLM turn;
8. invokes dynamic cloud TTS only for a successful free-form cloud reply.

The follow-up question is not generated by the SLM. The harness does not merge
the answer with the earlier call in version 1; every answer is a fresh SLM
turn. This is the same useful separation
demonstrated by VoiceTeller, adapted here to a combined audio-to-tool model
rather than separate ASR and text-SLM stages.

## Execution-layer contract

The execution layer is authoritative for:

- current robot pose, mode, battery and capability state;
- argument ranges, units, defaults and normalization;
- safety rules, collision constraints and confirmations;
- action dispatch, timeouts, cancellation and status reporting.

The SLM must not imitate this stateful behavior.

The demo implementation validates argument shape, required and actionable
fields, ranges, enums and unexpected fields before updating an in-memory
digital twin. It also consumes synchronized hardware state for conditions such
as refusing to open the trunk while the vehicle is running. Each action is
atomic: any reject leaves the twin unchanged. It is intentionally not a robot
driver or safety controller. Busy, missing-field, rejected and successful
outcomes already use the same result boundary that a real execution adapter
must implement.

## Response-audio ownership

The execute layer returns structured status and never chooses or plays audio.
The harness owns response selection and playback:

- every tool has fixed success, missing-field, detailed rejection and busy
  templates;
- those finite responses plus system fallbacks are rendered ahead of time and
  packaged in a checksum-verified manifest on the edge device;
- the edge runtime performs a read-only local lookup and never calls TTS for a
  tool result;
- only a successful free-form cloud answer calls the laptop-hosted OmniVoice
  service; a TTS failure plays a fixed local error clip.

## VAD and turn-taking

The initial VAD is an in-house, streaming energy/noise-floor baseline behind a
stable `VadEngine` interface. Endpointing policy and buffering are ours even
if a neural speech detector is evaluated later. The baseline supports:

- fixed-size 16 kHz mono PCM frames;
- adaptive noise-floor calibration and separate start/end thresholds;
- pre-roll so the first phoneme is retained;
- minimum-speech, end-silence and maximum-utterance limits;
- explicit start, end, timeout and rejected-segment events;
- a manual push-to-talk fallback for diagnosis.

Robot playback and motor noise make this different from ordinary browser
dictation. Version 1 is half-duplex: while the robot is producing TTS, the
harness does not open a new speech turn. Barge-in requires an evaluated echo
cancellation path and is deferred rather than relying on browser echo
cancellation. Initial thresholds are configuration values and must be tuned
against real robot recordings, not hard-coded into the demo.

See [`../src/vad/README.md`](../src/vad/README.md) for the
stream contract and evaluation criteria.

See [`speech-enhancement-review-2026-08-12.md`](speech-enhancement-review-2026-08-12.md)
for the recent-work review, local downstream benchmark and current frontend
decision.

## End-to-end demo

The top-level `demo/` application is the integration test surface. It imports
the VAD, SLM, harness and execution packages through their public interfaces;
it must not contain a second implementation of routing, VAD, slot checking or
execution.

The current page has a conversation timeline on the left and simulated
hardware on the right. Because the temporary SLM still exposes car functions,
the first digital twin is car-shaped. Its state projection is replaceable;
unknown robot state remains generic until the production catalog is frozen.

Version 1 is half-duplex. The browser stops sending microphone PCM as soon as
VAD finalizes an utterance. The server resets and reopens the listening gate
only after the browser reports response-audio completion. This is the demo's
turn-taking guarantee and is separate from browser echo cancellation.

## Evaluation axes

Evaluation will be reported separately for:

1. VAD false activations, missed speech, clipped onset, endpoint delay and
   segment purity;
2. route accuracy (`non_tool` versus robot action);
3. tool-name accuracy;
4. argument precision, recall and exact match;
5. missing-field behavior (correctly omitted versus hallucinated);
6. missing-field detection and fresh-turn follow-up behavior;
7. `non_tool` transcript WER/CER;
8. acoustic robustness (noise, distance, accent, silence, motor noise and
   robot playback);
9. component latency plus end-to-end latency measured from speech end to tool
   result or complete cloud response;
10. TTFT, TPS and real-time factor on edge hardware.
